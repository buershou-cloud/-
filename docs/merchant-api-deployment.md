# 商户 API 升级与宝塔部署

本次修改保留支付宝/抖音支付及分账入口。新的商户接入中心提供完整接口地址、产品列表、SDK与可分享的接入清单。商户 `/api/v1/merchant-api` 接口增加签名联通检查、订单归属/原通道限制、重复请求保护、可移植响应签名及持久通知重试。

## 升级前

1. 使用 Java 21。备份当前 JAR、外部配置、数据库及运行目录 `data/`；宝塔运行目录保持固定。
2. 生产启用原有 MySQL 配置。订单/退款保护复用原有表和唯一键，不需要新增业务表；无数据库模式只能用于开发。
3. 给每个商户绑定支付通道，检查状态为“正常”；无绑定商户现在会被拒绝，停用商户不能再调用签名 API。
4. 在支付通道设置里配置公网的**网关通知地址**。支付宝为 `https://你的域名[/子路径]/api/v1/alipay/notify/通道ID`，抖音为 `https://你的域名[/子路径]/api/v1/douyin/notify/通道ID`。商户网站自己的 `notifyUrl` 另外在下单中提交，不能填到上游网关通知地址中。
5. 宝塔反向代理保留 Host、X-Forwarded-Proto 等正确代理头，将商户 API、平台通知与静态接入资料路径交给 Java 服务。商户 API 不使用后台登录 Cookie；不要在反向代理额外加后台登录拦截。

## 持久目录和密钥

可在外部 `application.yml` 配置：

```yaml
payment:
  merchant:
    platform-key-file: /www/wwwroot/payment-data/platform-rsa.properties
    notify-outbox-directory: /www/wwwroot/payment-data/merchant-notifications
```

未配置时，相对启动目录默认使用 `data/platform-rsa.properties` 和 `data/merchant-notifications`。服务首次生成平台 RSA 密钥文件，以后重启加载同一文件；文件损坏或公私钥不匹配会启动失败，不会悄悄换公钥。私钥文件只能由运行账号读取，不要放在宝塔可直接访问的静态目录下，也不要提交 Git。

旧版本的平台密钥在进程内随机生成，无法从原数据库还原旧私钥。**首次升级后，需要商户重新复制一次平台公钥**；后续升级只要保留该密钥文件，平台公钥保持稳定。商户自己的 MD5 密钥和 RSA 密钥按原配置保留。备份与恢复时应一起保存数据库、平台密钥及通知队列。

多个实例必须使用同一平台密钥和共享通知目录，并确保共享文件系统支持文件锁与原子替换；不要让每个实例各自生成平台密钥。单机宝塔部署通常使用一个实例。请求 nonce 防重放缓存当前仍在单实例内存中；这不是跨实例/重启持久防重放账本。支付和退款重复提交保护依赖持久数据库的唯一键与订单锁。

## 通知确认和重试

支付通知先保存至本地通知目录，再发送至商户地址。每5秒扫描队列，失败依次等待5秒、30秒、60秒、5分钟、15分钟、1小时，之后每小时继续尝试；进程重启仍会恢复。接收方必须返回 HTTP 2xx 和文本 `success` 才确认（接收器容许大小写及前后空白，建议固定返回小写纯文本）。平台不跟随通知重定向。

通知文件记录原订单、地址、业务负载、次数、下次重试时间和投递结果；不包含商户密钥。每次发送按商户当前签名设置签名。商户修改密钥或默认签名模式时，需要同步更新接收方配置。已经成功送达的事件文件会保留，用于去重；不要日常删除这些文件。待投递文件的 `delivered=false` 和日志 `Merchant notification awaiting retry` 可用于排查。

商户成功主动查询支付结果时会补排通知。此补偿不代替完整业务对账：网站仍应定期查询自己的未完成支付。退款结果不确定时在后台核对原退款请求，不能用新的请求号重新退一次。

## 对旧接入的影响

- 商户登录仍用商户号与 MD5 密钥。公开 `demoLogin=true` 不能再绕过认证；只有已经登录的管理员可使用快捷进入功能。
- MD5/RSA2 请求签名方式和原接口路径保留。旧调用未发送 `X-Merchant-Response-Signature` 时保留原响应格式；新SDK使用 `canonical-v1`，响应数值表示为字符串。
- 查单/取消/退款允许只传一个订单号；传两个必须匹配，且必须属于当前商户。操作固定原通道。
- 支付和退款在调用上游前占用请求号。重复请求返回409，不再重复调用通道，也不自动跨渠道重试。未知结果保留占位，需查原单/核对，避免重复扣款或退款。
- 商户支付 `extra` 不能覆盖订单号、金额、身份和通知等保留字段。合法的商品/产品扩展参数仍按现有产品能力处理。
- 后台/收银台和原支付宝分账保持原入口；商户回调重写仅应用于已验证商户 API 创建的支付。公开收银台下单也使用原子订单占位，重复订单号被拒绝，未知结果不会换通道重下单，以免绕过商户订单保护；应先查询原单再处理。公开请求不能伪造内部商户 API 标记，也不能用扩展字段覆盖订单号、金额或上游操作方法。

## 上线验收

先启动新 JAR，确认健康接口及商户页面可访问，再运行SDK `check`。用真实已开通产品进行小额付款，验证网站收到平台签名通知并只更新一次订单；分别检查主动查询和退款。故意让网站首次通知返回500，再恢复200 `success`，确认后续重试生效。重启服务后再次验平台签名，确认没有更换平台公钥。

本地自动测试覆盖协议、密钥加载、通知重试及路由保护；没有生产支付机构密钥时，不能把本地检查等同于真实支付宝/抖音支付验收。
