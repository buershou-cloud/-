# 订单管理中的收款、分账与代付记录

订单管理支持按全部、收款、分账、代付查看记录。分账请求号、代付单号可使用订单号筛选框查询，平台单号、通道和创建时间筛选也作用于支出记录。

收款数据继续来自 `pay_order`；分账流水保存到独立的 `profit_sharing_record`；代付直接读取既有 `merchant_payout`。支出不会伪造成收款订单，也不参与收款营业额、退款额或可分账收款单统计。列表刷新不会重新付款或重新分账。查看支出记录不会提供收款订单的退款、改已完成、删除或再次分账操作。

## 新分账流水

系统记录支付宝和抖音分账的原请求号、通道、原收款订单或平台交易单号、金额及状态。对于多个接收方，分账金额显示本次请求的合计金额，完整请求与结果用于服务端核对；列表接收方脱敏显示。

受理或处理中不代表最终到账。同步结果、原请求查询和抖音已验签通知用于更新原分账流水。结果未知时应使用原请求号查询或联系支付平台核对，不能为了在列表中显示记录而换号再分账。成功状态不能被迟到的处理中响应降级。

分账发送前先保存请求，保存失败不发送资金请求。单次分账调用只使用选定通道，不因结果不明或记录保存失败而自动切换通道；其他支付接口的通道路由保持原逻辑。同通道同请求号的已成功请求返回原结果，已有未确认或失败记录不能通过重新提交来再次发送分账，参数不同也会拒绝。先核对原请求，明确需要新增分账时使用新的请求号。

管理页面会指定单一通道。直接调用分账 API 时也应在 `channelIds` 中只填写原支付通道，并在后续查单时保持一致；去重范围是通道和请求号组合。支付宝保留原有的隐式选路方式，省略通道并不能保证多次调用选择同一通道。

## 代付状态查询

支付宝和抖音代付分别使用原记录保存的平台及通道查询。列表的“刷新记录”只重新读取本地数据；目前没有代付定时查单，最终状态由平台结果通知或“查询原单”更新。

在代付记录或订单管理中点击“查询原单”，页面会立即显示原单号、平台、通道和查询进度，按钮显示“查询中…”。查询结果显示在当前页面的记录旁；处理中、成功、失败或查询未确认分别说明。查询失败不能作为转账失败的依据，列表刷新失败也不能覆盖已经取得的查询结果。

“查看结果”显示本地保存的记录，不代表已向平台重新查询。只有明确显示原单查询完成后，才取得了本次查询返回的结果；平台仍在处理中时不代表最终到账，也不能仅凭该状态判断余额不足。

支付宝查单接口本身报错、回包无法解析、状态缺失或原单信息不匹配，都不能作为代付失败的依据。本次查询会明确提示未确认结果；尚无终态的记录保留待核对状态，已有成功或失败终态不因查询错误改变。只有平台明确返回原单失败状态，才能确认代付失败。创建代付后的回包解析失败也按结果未知处理，不自动重转。

原单查询只调用平台查单接口，不会再次转账。重复点击同一笔正在查询的订单不会重复发送查询，不同订单的结果按原单号显示。回调未同步或平台仍未给出终态时，可到对应商户的平台账单中用原平台单号核对。

## 既有历史

- **历史代付**：仍在 `merchant_payout` 表中的记录会直接显示；订单管理按条件查询完整历史，不受商家代付页最近 200 条的限制。
- **历史分账**：旧版本仅给原收款单保存“已分账”标记，没有保存完整分账流水。这个标记不能证明具体请求号、分账次数、接收人和金额，升级不会凭空生成这些明细。原收款单上的标记保留。应凭原请求号、支付平台账单或原始记录核验；不要重新分账补记录。
- **外部订单**：仅有平台交易单号的分账也需保存独立流水，不能为此创建虚假的收款订单。
- **已删除的数据**：升级无法恢复被删除的数据库记录。可从数据库备份或支付平台账单核对，不能通过重复付款恢复。

## 只读接口

后台登录后可调用 `GET /api/v1/orders/operations`。支持 `beginTime`、`endTime`、`outTradeNo`、`tradeNo`、`channelId`；其中 `outTradeNo` 对支出匹配对应业务请求号，分账还可以关联原收款单查询。

响应包含 `records` 数组和 `warnings` 数组；其中一种记录读取失败时，返回另一种可读取的记录并明确警告列表不完整。记录的 `recordType` 为 `PROFIT_SHARING` 或 `PAYOUT`，金额单位为元。无法核实历史金额时允许 `amount: null`，前端显示“金额未记录”，不能填零或取原收款金额冒充分账金额。列表不返回原始密钥、支付密码或明文收款账号。

读取记录失败时页面会提示，不能把加载失败当作无记录或付款失败。代付成功后如果仅刷新失败，应保留成功结果并单独刷新，切勿重新提交转账。

## 部署与持久化

同一版本也修正手机在支付宝内扫商户收银台入口后的提交方式：`ALIPAY_PAGE` 和 `ALIPAY_DIRECT_PAGE` 保留原产品、通道及 `alipay.trade.page.pay` 接口，使用 `ALIAPP` 钱包模式直接提交原签名 POST 表单。电脑和外部手机唤起支付宝的流程保持原逻辑。支付宝官方 SDK 说明了同一接口的 [钱包集成方式](https://github.com/alipay/alipay-sdk-java-all/blob/master/v2/src/main/java/com/alipay/api/domain/AlipayTradePagePayModel.java) 和 [POST 表单返回方式](https://github.com/alipay/alipay-sdk-java-all/blob/master/v2/src/main/java/com/alipay/api/response/AlipayTradePagePayResponse.java)。这次修改不切换 WAP 或其他支付产品；最终收银台显示仍需部署后在支付宝内实机验收。

2026-10-09 的更新包含查询反馈和代付结果判断修正，不需要新增数据库表。宝塔更新时先备份并停止 Java 项目，替换原 `target/payment-gateway-0.1.0-SNAPSHOT.jar` 后按原 Java 21、工作目录和启动参数启动；保留 `data/admin-auth.properties`、现有数据库和外部配置。浏览器强制刷新后，原单查询应立即显示进度。上传源码时需执行 `mvn -DskipTests package` 重新打包；不要执行 `mvn clean`，避免清除可能存在的 `target/data`。

生产环境须保持 `payment.database.enabled=true` 及现有 MySQL 配置。数据库模式启动时会检查 `profit_sharing_record`，仅缺表时自动建表；表已存在且可读时不要求应用账号具备建表权限。如果应用数据库账号没有建表权限，请在更新 JAR 前，由数据库管理员执行 [新增表脚本](../database/mysql/20260928_add_profit_sharing_record.sql)，并授予应用账号该表的读写权限。脚本只新增分账流水表，不清空或改写原收款、代付及分账关系表。

无数据库的开发模式仅在当前进程内保存分账流水，重启后不保留；代付本身仍要求数据库。记录表创建失败不会被当作记录已持久化，需根据启动日志处理后再启动新版。

抖音完整分账结果通知或使用原请求号查询所得的可核实结果可以补记独立流水；缺失字段保持未知。支付宝目前没有在本系统接入同类分账查单补记入口，历史需凭原始请求记录与平台账单核实。补记不会发起资金操作。
